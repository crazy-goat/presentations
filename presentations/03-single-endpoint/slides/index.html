Scaling application

Scaling application

  • Available Options
  • Based on CPU
  • Based on Request per second
  • Custom metrics using KEDA
  • Of course, we chose the custom metrics option

Scaling application

(Dis)advantages of CPU base scaling

  • It is straightforward to implement
  • It works with a cpu-based load
  • It does not work with a high IO-based load
  • Example: It will not scale on high network latency

Scaling application

(Dis)advantages of RPS base scaling

  • It is straightforward to implement
  • It works if you have stable response times
  • All endpoints should have similar response times
  • It will not scale on high network latency

Scaling application

We choose to use active PHP-FPM workers as a scaling metric

  • It is a little harder to implement
  • pm=static and pm.start_servers=20
  • If avg active worker > 15 scale up
  • We test this on local k8s cluster using wrk and ab
  • It works well, with small number of connection
  • On lots of connection it created a scale bomb 💣
  • Unfortunately, we only discovered this in the production environment

Scaling application

The PHP-FPM counting connection problem

  • PHP-FPM has a problem with counting active processes
  • Example: It could return 3347 when pm.max_children=20
  • After two days of investigation, we found the bug
  • It only happens when fastcgi_keep_conn on directive in the nginx
  • Hot-fix: disable this line in config
  • Report bug to PHP: https://github.com/php/php-src/issues/14212

Scaling application

Tuning pod size and scaling params

  • We started with 20 workers on MVP
  • It was good when we had response times about 100ms
    • one worker: 1/100ms = 10 req/s
max per pod: 20 workers * 10 req/s = 200 req/s
scaling up: 15 workers * 10 req/s = 150 req/s
1600 req/s / 150 req/s ~= 12 pods
  • We made some optimization to code and data structures
  • Response time went down to 30-40ms
  • And then...

Scaling application

New response times changed everything

  • New response times were ~15ms
  • 20 workers on one pod was waaaay to much
    • one worker: 1/15ms ~= 65 req/s
max per pod: 20 workers * 65 req/s = 1300 req/s
scaling up: 15 workers * 10 req/s = 950 req/s
1600 req/s / 950 req/s ~= 2 pods
  • In theory, we don’t need to scale at all.
  • The HA requirements already assumed at least 2 pods.
  • But there’s a catch...

Setting CPU requests and limits

  • 1/3 is IO (redis and mognodb) 2/3 is PHP
  • We need to do some math again.
    • 15 workers * 0.667 ~= 10 cores
  • It will be hard to allocate that many resources on a crowded node.
  • In case of failure, the remaining pod will get a lot of traffic.

Cat Head Problem

  • Two peaks: one in the morning, bigger one in the evening.
  • Medium traffic during the day.
  • Minimal traffic during night hours.
  • The difference between the lowest traffic and the peak is 75x.
  • We don’t want to pay for 20 cores at night.
  • That’s why we had to do the math again...

Cat Head Problem

  • For 6 hours during the day, we have very low traffic.
  • We want to pay as little as possible during this period.
  • We also want to scale very quickly to meet traffic demands.
  • We need a reserve in case of a failure.
  • Or in case of a sudden traffic surge.
  • So we came up with this...

Cat Head Problem

  • Each pod serves around 20 req/s before scaling up.
  • At night, we only have two pods.
  • At peak load, we expect to have around 80 pods.
  • Large reserve - in theory, one pod can handle traffic up to ~200 req/s.
  • Losing even a few pods is not a problem.
  • The application looks more robust when it has many pods.
