Symfony messenger batch processing - game changer

    public function __invoke(Message $message, Acknowledger $ack = null): mixed {
        return $this->handle($message, $ack);
    }

Chasing a rabbit

Symfony messenger batch processing - game changer

  • BatchHandlerInterface does not speed up processing
  • Instead, it allows for the use of bulkWrite in MongoDB.
  • This significantly reduces traffic between the consumer and the database.
  • Allows ordered=false for parallel writes.
  • Also added w=1&journal=false for all consumer.
  • We achieved around 450 msg/s.
  • With 3 consumers, we achieved the desired performance.

Know your data!

Setting journal=false is not recommended for critical data. However, in our use case, we can rebuild the data very quickly. It is not a critical issue if a customer temporarily sees recommendations in a different order.

Setting ordered=false means that queries in a batch are executed in a random order. This can lead to unpredictable results. In our case, messages in the queue never refer to the same records. This way, we don’t have any problems with data being overwritten in the wrong order.

Know your data!

Setting w=1 is not recommended if you can't afford replication lag. In our case, the fact that the data on the secondary would appear in a few seconds didn't matter.

  • but only support read-write separation for cluster

Wrong way to make cache

In the initial phase of our application, we had two problematic queries that took 90% of the time of all queries

  • The first was a query of the type 
    IN(id1, ... id200)
  • The second involved selecting approximately 1,500 products based on a complex filter.
  • Each of these queries took 10-30 milliseconds.
  • We could cache results for about 5 minutes.
  • But this solution wasn't optimal.

Wrong way to make cache

  • Store offers approximately 4.5 million products.
  • The cache size exploded, and there were large number of evictions.
  • The hit/miss ratio was terrible.
  • For popular products, the speedup was indeed noticeable.
  • However, for most products, implementing the cache caused a slowdown.
  • Cache miss -> database query -> cache store

Know your data!

After analyzing the data, it turned out that instead of maintaining a cache for individual products, we could recalculate the necessary data for entire product groups. This gave us some hope; the only thing left to do was to see if we could perform these recalculations quickly enough.

Cache done right

  • For each store we keep about 80 keys
  • For brand its about 2000 keys
  • The entire cache takes 25MB RAM / 12,5kb per key
  • It takes 13 seconds to generate cache
  • We fetch two keys per request
  • Depending on the product, the cache is an array containing approximately 100 - 10,000 entries
  • To reduce decoding time and data volume, we used igbinary
  • This decision caused problems...

Cache done right

  • Despite 100% coverage of the problematic queries, they still sometimes executed.
  • It turned out that the cache was not generated for larger tables.
  • Symfony cache does not throw exceptions if the cache fails to be written.
  • After a little investigation, it turned out that we can't save arrays larger than 3338 entries.
  • Later, it turned out that larger arrays can be saved.
  • An array can't be saved if it has a key "3338"

The Hidden Magic of Number 3338

  • Why array key 3338 is problematic
  • 3338 in hex is 
    0D 0A
  • 0D => 015
    in ASCII is Carriage Return (\r) 
  • 0A => 012
    in ASCII is Line Feed (\n)
  • predis use 
    \r\n
    as command separator in pipeline
  • Reported: https://github.com/predis/predis/issues/1574
  • Fixed not released yet.

Cache done right - but we can do better

  • We can do it better because the cache size is only 25MB
  • So the entire cache will easily fit in the APC
  • The only problem is that we cannot save the cache to APC within the cron command.
  • We can use Symfony Chain Cache Adapter for this
  • And use redis only to distribute keys to application pods
  • This solution worked incredibly well
  • Even a little too well...

Mongo

Why we chose mongodb as the database

  • We had the choice between MySQL and MongoDB.
  • High performance for writes and reads for PK.
  • Easy HA setup with Replicaset
  • High data compression
  • No schema - good for prototyping.

Mongo

  • Why did we choose version 7.0 instead of 8.0?
  • At first, we started with version 8.0 on dev machines.
  • Then we prepared a local version on k3d to test replicasets.
  • Next, we deployed it on test servers.
  • Up to this point, everything worked fine with version 8.0.
  • But on production servers, we had an older Mongo operator.
  • This operator did not support version 8.0.

Mongo

  • There was no option to quickly upgrade the operator.
  • So we had to switch to version 7.0.
  • It is a pity, because version 8.0 has many performance improvements.

Mongo - lesson learned

Keeping everything in one collection with big documents is not a good idea

  • This design is only good for simple key-value data.
  • If a query is not covered by an index, reading can be very expensive.
  • Even to get one field, the whole document must be read.
  • With big updates, frequent relocation may happen.
  • Parallel updates - you must remember about document lock.

Mongo - lesson learned

Running MongoDB in Kubernetes vs. bare metal

  • Make sure Mongo runs on dedicated CPUs.
  • No direct access to fast persistent disks.
  • If using PVC, check performance limits.
  • Example: on GCP, 32GB pd-ssd gives ~4000 IOPS and 15MB/s.
  • Because of this, we had to choose a much bigger disk than we needed.
  • Also remember about IOPS limits for the instance.

Mongo - lesson learned

  • IOPS are not the biggest problem.
  • The main issue is high latency of such disks.
  • Surprisingly, read latency is higher than write latency.

Mongo - lesson learned

  • It is crucial that our dataset fits into RAM.
  • But what if the dataset does not fit?
  • By default, Mongo splits memory: 50% WiredTiger, 50% page cache
  • bare metal: reduce WiredTiger cache, Change compression from snappy to zstd
  • K8s: Increase WiredTiger to 80%. Hope the node has enough free RAM for page cache

What if the dataset does not fit RAM?

  • Just reduce your data set
  • Remove old data
  • Use more compressed data structures
  • It's usually not difficult, you just have to do it.
  • In our case, 2 weeks of work was enough

What if the dataset does not fit RAM?

  • Look for free RAM in your cluster
  • If your cluster is mainly composed of applications, there will definitely be a lot of free RAM.
  • Ask for more RAM. On GCP, it's 7-8 times cheaper than CPU.

Mongo - indexes

  • Index size reduction
  • In our case, only ~20% of products are active.
  • The rest are archived products, no stock, or new items.
  • Mongo allows creating indexes only on part of a collection.
  • To use such an index, the query must match the index filter.
  • This reduces the amount of RAM needed for indexes.
  • Indexes are not updated if the write does not match them.

Mongo - indexes

createIndex(
    {"brand": true, "store": true, "sku": true},
    {"partialFilterExpression": { "isSaleable": true } }
)

In our case the size reduction is about 10 times

Mongo - in hell

  • Why do we need to query and cache thousands of SKUs?
  • All recommendations come from an external system as a list of SKUs.
  • For each product, we get several vectors, each with 100–1500 SKUs.
  • Our system must constantly calculate which SKUs are "buyable".
  • Because these lists are random, we can only select them using query IN(...).

Mongo - indexes

Here is an example query that returns active SKUs for a given vector.

"filter": {
    "brand": "foo",
    "store": "bar",
    "isSaleable": true,
    "sku": { "$in": ["SKU-0001", ... "SKU-2000"] },
"projection": { "sku" : true}

With a few SKUs in IN(), the query works fine. But with 1000 SKUs in IN(), the query is not efficient.

Mongo - in hell

  • How did we solve this problem?
  • A cron job query all “buyable” SKUs and stores the result in Redis.
  • From Redis, we sync the list of active SKUs to APCu cache.
  • Our system must constantly calculate which SKUs are "buyable".
  • When showing recommendations for a product, we get recommendation vectors from MongoDB.
  • Then we use array_intersect to compare both lists.
$validSKUs = array_intersect($similarSKUs, $allValidSKUs);

Networking cost

  • On an average day, we serve approximately 16.5M recommendations
  • Each request is approximately 35kb of data
  • This gives us about 560GB of data per day
  • And approximately 16TB of data per month.
  • 1GiB egress costs around €0.085
  • 16TiB costs around ~€1300
  • Twice as much as our application cost without any scaling

Networking cost

  • How to limit the amount of outgoing data
  • By enabling compression for json responses for php
  • Configuration is simple and has minimal impact on response time
server {
        gzip on;
        gzip_vary on;
        gzip_min_length 1024;
        gzip_comp_level 6;
        gzip_types
            application/json
        ...
    }

Networking cost

  • Compression results:
  • Response size from 35kb -> 3.6kb
  • Monthly transfer from 16TB -> 1.8TB
  • Monthly transfer cost from ~€1300 -> ~€160
  • Adding few config lines, we reduced the egress costs by 8x
