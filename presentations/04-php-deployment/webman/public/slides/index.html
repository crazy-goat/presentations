Era: FTP

How it looked

  • Zend IDE / Eclipse with built-in FTP sync
  • FileZilla open on production
  • Upload file by file
  • Pray nobody else is editing the same file

First deployment

  • Upload app.tar.gz via FTP
  • But how do you unpack it? No SSH access...
  • Solution: deploy.php — a script that unpacks the archive
  • Run it in the browser. Done. Now delete it (or forget — security nightmare)
  • On larger projects: request timeout halfway through 🙃

Real world: Sote ~2005

Polish e-commerce platform — classic FTP era

  • Installation: upload sote.tar.gz, run install script in browser
  • Set permissions, configure DB, set up paths manually
  • Updates delivered as .diff files (unified diff format)
  • A PHP script parsed and applied the diff — basically patch, but in PHP, in the browser
  • Hotfixes and debugging: upload the fixed file directly via FTP

Real world: Sote 5.0 ~2008

  • Installation: copy a single installer.php to the server, open in browser
  • It downloads the package itself, checks dependencies, runs setup
  • Modular architecture — PEAR packages (Composer didn't exist yet)
  • Updates: upgrade individual modules, not the whole shop
  • File integrity check before install — did not overwrite client customizations
  • Custom plugin system, built on Symfony 1.0
  • Fixes and debugging: delivered as a PEAR package update, not raw FTP
This was ahead of its time — essentially a package manager + installer + update system built in 2008.

The pain

  • No versioning — "I overwrote prod"
  • No rollback
  • Binary vs ASCII transfer mode — corrupted files, broken encodings
  • File permissions — chmod everything via FTP client
  • Symlinks — FTP doesn't support them
  • "Works on my machine"

Think this era is over?

Think again.

There are entire armies of WordPress sites still maintained exactly this way.

Era: Own scripts

deploy.sh


#!/bin/bash
rsync -avz --exclude='.git' ./ user@prod:/var/www/app/
ssh user@prod "cd /var/www/app && php bin/console cache:clear"

Real world: Komputronik.pl ~2015

  • CI on Jenkins — pull from git to stage, run tests
  • Tests pass → rsync to 4 prod instances, sequentially from stage
  • Mandatory cache clear after each deploy
  • ~10 deploys per day
  • Revert: git revert + redeploy
  • DB migrations run at night — no instant DDL in MySQL back then
  • Deploy access: wizards only — not everyone had the power
  • Script in Bash... with fragments in Ruby
  • Debugging: SSH directly into prod

The pain

  • How do you sync to multiple servers?
  • Migrations — where do you run them? On which server? Before or after rsync?
  • High PR volume — who triggers the deploy? When?
  • Night deploys — "let's do it at 2am when traffic is low"
  • Hard to test outside your own dev environment
  • No documentation, no standards — every company had their own
  • Bus factor: 1 — only the author knew how it worked
  • Written in whatever the author liked — Ruby, Perl, Bash, Make...

Era: Ansible

How it works


- name: Deploy PHP app
  hosts: production
  tasks:
    - name: Pull latest release
      git:
        repo: git@github.com:org/app.git
        dest: /var/www/releases/{{ release_name }}
    - name: Install dependencies
      composer:
        working_dir: /var/www/releases/{{ release_name }}
    - name: Run migrations
      command: php bin/console doctrine:migrations:migrate --no-interaction
      args:
        chdir: /var/www/releases/{{ release_name }}
    - name: Switch symlink
      file:
        src: /var/www/releases/{{ release_name }}
        dest: /var/www/current
        state: link

What got better

  • Multiple releases kept on server — rollback = flip a symlink
  • Run migrations on one node first, then roll out code
  • Rolling release — replace nodes one at a time, zero downtime
  • Native multi-node support out of the box

The pain

  • Server must have PHP, nginx, php-fpm installed and configured
  • Environments drift over time — "works on staging, fails on prod"
  • Requires SSH access and Python on every target server
  • Why do I need Python on a PHP server?

The common problem

FTP, scripts, Ansible — three different eras, one shared flaw:

The application and the environment were managed separately.

  • App updated regularly — environment left to age on its own
  • Dev team owned the code, ops team owned the server
  • Every upgrade became a negotiation
  • "It worked last time we deployed..."
  • Dev environment looked nothing like prod
  • Setting up a new dev environment: 2–3 days of README spelunking
  • Abandoned systems were nearly impossible to recreate

Real world: The forgotten microservice

A microservice. Running on bare metal. On a very old Ubuntu.

Need to update the LDAP extension.

App refuses to run on anything newer.

Must compile on the existing OS.

Real world: The forgotten microservice

No package mirror available for that Ubuntu version.

Found one mirror. In Portugal.

Download time estimate: 7 days.

It would have been faster to fly there with a hard drive.

Real world: The forgotten microservice

Solution:

  • Build a local mirror from what was on disk
  • Rebuild the extension inside an LXC container
  • Ship the container

The app was eventually replaced.

Real world: Gerrit on bare metal

The entire organisation's source code. CI. Everything.

On a single physical server. Struggling for a long time.

Updates failing. Nobody wanted to touch it.

Real world: Gerrit on bare metal

Power outage in the server room.

Server does not come back up.

Need to recover data from the disks — but the hardware RAID is model-specific.

Had to find a donor machine with identical RAID hardware just to read the disks.

Real world: Gerrit on bare metal

Data recovered. Migrated to an LXC container. Ran on a cluster.

Eventually replaced with a self-hosted GitLab.

Lesson: if you can't recreate it, you can't recover it.

Era: Docker

The big shift

Application and environment packaged together — the image is the deployment artifact.


FROM php:8.3-fpm
COPY . /var/www/app
RUN composer install --no-dev
    

# docker-compose.yml
services:
  nginx:
    image: nginx:alpine
  php:
    build: .

Architecture

In practice: nginx + php-fpm bundled in one container, managed by supervisord


┌──────────────────────────────────┐
│          one container           │
│                                  │
│  ┌──────────┐   ┌─────────────┐  │
│  │  nginx   │   │   php-fpm   │  │
│  └──────────┘   └─────────────┘  │
│        supervisord               │
└──────────────────────────────────┘

What got better

  • Dev = prod — same image, same behaviour
  • Onboarding: docker compose up instead of 2–3 days
  • Rollback = pull previous image tag
  • Environment isolation per project
  • Abandoned system? Just keep the image.

The pain

  • nginx + php-fpm in one container — need supervisord or s6 to manage both processes
  • Bundling everything together makes images large and complex
  • Heavy base images — php:8.3-fpm is ~490 MB of Debian
  • Docker alone didn't solve clustering — Docker Swarm came later
  • Databases still often run on bare metal — scaling requires planning
  • New tooling to learn: Dockerfile, networking, volumes, compose...

Era: Kubernetes

What Docker alone doesn't solve

Clustering & availability:

  • Run across multiple nodes
  • Automatic failover — dead container? K8s restarts it
  • Self-healing, health checks built in

What Docker alone doesn't solve

Scaling & traffic:

  • Horizontal Pod Autoscaler — scale on CPU/memory/custom metrics
  • Built-in load balancing between pods
  • Rolling deployments — zero downtime out of the box
  • Service discovery

What Docker alone doesn't solve

CI/CD & GitOps:

  • ArgoCD / Flux watch your git repo
  • Push to git = deploy to cluster
  • Declarative config — cluster state is always in sync with repo

Architecture: PHP in Kubernetes

In K8s "one process per container" is the right way — nginx is back as a sidecar


┌─────────────────────────────────────┐
│                 Pod                 │
│  ┌──────────────┐ ┌──────────────┐  │
│  │    nginx     │ │   php-fpm    │  │
│  │   sidecar    │ │  container   │  │
│  └──────────────┘ └──────────────┘  │
└─────────────────────────────────────┘

The pain

  • Enormous complexity — needs a dedicated platform team
  • Three screens of YAML to deploy Hello World
  • The tooling ecosystem is itself complex: ArgoCD, Flux, Helm, Kustomize...
  • Networking, storage, ingress — each is its own rabbit hole
  • Overkill for small projects
  • You can throw more pods at a slow PHP app — but that's treating the symptom, not the cause

We solved deployment. But...

Our Docker images are still:

  • Heavy — hundreds of megabytes of OS, libraries, tools
  • Complex — nginx, php-fpm, supervisord, dozens of system packages
  • Vulnerable — every dependency is a potential attack surface

We containerised the mess. We didn't remove it.

Does it have to be this way?

Node.js


const http = require('http');
http.createServer((req, res) => {
  res.end('Hello World');
}).listen(3000);
    

node server.js
# Done. No nginx. No fpm.

Simpler architecture — but still ships with node_modules 📦

Go


func main() {
    http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintln(w, "Hello World")
    })
    http.ListenAndServe(":3000", nil)
}
    

go build -o app
./app   # one binary, zero dependencies

No dependencies. Small image. Fast startup. Fast execution.

Why is PHP different?

PHP was designed as CGI — request → process → die

nginx and php-fpm are a workaround for that limitation.

But does it have to stay that way?

php -S

PHP has a built-in web server


php -S 0.0.0.0:8080 public/index.php

It works. No nginx. No php-fpm.

But...

  • Single-threaded — one request at a time
  • PHP docs: "not designed to be used on a public network"
  • Still the classic PHP model — state cleared after every request
  • Development only

Architecturally simpler — but PHP still drags along a full runtime and its dependencies.

A proof of concept. Not a solution.

ReactPHP / AmPHP

Event loop in PHP

  • Long-running PHP process — code loaded once, not per request
  • One process handles many concurrent connections
  • No nginx. No php-fpm.
  • Performance comparable to Node.js

The trade-off

  • Callback hell / promise chains — async all the way down
  • Can't use blocking PHP functions — file_get_contents, standard PDO...
  • Requires rewriting the entire application
  • Steep learning curve for PHP developers
  • CPU-intensive operations block the entire event loop
  • Long-running processes — not all libraries and frameworks are designed for this

A valid approach — but not ideal:

  • Still requires a full PHP runtime with all its dependencies
  • Not all workloads are a good fit

Workerman

Multi-process, synchronous PHP

  • Battle-tested in production — massively popular in China
  • Multi-process model — each worker is a separate PHP process
  • Synchronous code — write normal PHP, no async, no callbacks
  • Webman — HTTP framework built on top of Workerman

How it looks


// Normal synchronous PHP — no async required
public function index(Request $request): Response
{
    $users = User::all();
    return response()->json($users);
}
    

php start.php start
# Workers: 4 processes
# Listening: http://0.0.0.0:8787

What you gain

  • No nginx. No php-fpm.
  • Application code loaded once per worker — not on every request
  • ~10x faster than traditional php-fpm

Limitations

  • Existing libraries work without modifications — but watch out for memory leaks
  • Long-running processes need careful state management
  • Not all frameworks work out-of-the-box — Symfony requires adapters
  • Simple apps: use Webman directly

We have performance. We have simplicity.

No nginx. No php-fpm. Synchronous code. Fast.

To run a PHP application, do we need:

  • A shell?

Or do we just need... PHP?

Statically compiled PHP

static-php-cli

Compile PHP with all extensions baked in — no shared libraries, no OS dependencies.


bin/spc build "bcmath,curl,openssl,pdo,pdo_mysql,zip" \
    --build-cli

Result: a single php binary that runs anywhere.

FROM scratch


FROM scratch
COPY --from=builder /app/php /php
COPY --from=builder /app /app
ENTRYPOINT ["/php", "/app/start.php"]
  • Zero OS
  • Zero shell
  • Zero attack surface

How small can we go?

ImageSize
php:8.3 (Debian)~580 MB

What's in the image

Only two things:

  • The php binary
  • Your application files

Nothing else.

Security bonus

No shell means no shell exploits.

No package manager means no supply chain attacks through the OS.

But — you can still docker exec into the container and use the PHP binary to run arbitrary code.

The attack surface is smaller, not zero.

🐉 Here be dragons

What this means in practice

  • Works in my environment — your mileage may vary
  • Not battle-tested in large production projects
  • Hard to integrate into standard CI/CD pipelines
  • Limited community support and documentation
  • Use with care. Not a drop-in for production tomorrow.

Webman as a single binary

PHP + Workerman + app = one file


# static-php-cli builds PHP as a self-executing stub (micro)
bin/spc build "bcmath,curl,openssl,pdo,pdo_mysql" \
    --build-micro

# Bundle app.phar into the binary
cat micro.sfx app.phar > myapp
chmod +x myapp

./myapp
# Listening: http://0.0.0.0:8787

Deploy = copy one file


FROM scratch
COPY myapp /myapp
ENTRYPOINT ["/myapp"]

The Go dream, in PHP.

Limitations

  • PHP compilation takes time — but compile once, reuse until extensions change
  • Not all extensions can be compiled statically
  • Example: New Relic — requires a dynamic .so library, won't work here
  • Still experimental territory

Symfony on scratch

Does it work with a full framework?

Symfony + statically compiled PHP + FROM scratch — yes, but:

  • Requires an adapter to boot Symfony inside Workerman
  • e.g. crazy-goat/workerman-bundle
  • Unusual startup model — not php bin/console server:run

What works, what doesn't

  • ✅ Routing, controllers, Twig, Doctrine
  • ✅ FROM scratch image
  • ⚠️ Cache must be pre-warmed before building the image
  • ⚠️ Writing to disk can be tricky — e.g. logs go to a shared file across workers
  • ⚠️ Some extensions require separate compilation
