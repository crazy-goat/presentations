FTP

The Dark Ages

How it looked

  • Zend IDE / Eclipse with built-in FTP sync
  • FileZilla open on production
  • Upload file by file
  • Pray nobody else is editing the same file
  • Wonder why ą, ę, ó turned into ??? on the server

Real world: Sote 3.x/4.x (2005)

Polish e-commerce platform — classic FTP era

  • Distribution: download or on CD
  • Installation: upload sote.tar.gz, run an install script in browser
  • Set permissions, configure DB, set up paths manually
  • Updates delivered as .diff files
  • A PHP script parsed and applied the diff — basically patch, but in PHP, in the browser
  • Hotfixes and debugging: upload the fixed file directly via FTP
f

Real world: Sote 5.x (2008+)

  • Installation: copy a single installer.php
  • It downloads the package itself, checks dependencies, runs setup
  • Modular architecture — PEAR packages (Composer didn't exist yet)
  • Updates: upgrade individual modules
  • File integrity check — did not overwrite client customizations
  • Custom plugin system, built on Symfony 1.0
  • Fixes and debugging: delivered as a PEAR package update, not raw FTP
This was ahead of its time — essentially a package manager + installer + update system built in 2008.

The pain

  • No versioning — "I overwrote prod"
  • No rollback
  • Binary vs ASCII transfer mode — corrupted files, broken encodings
  • File permissions — chmod everything via FTP client
  • Symlinks — FTP doesn't support them
  • "Works on my machine"

Think this era is over?

Think again.

There are entire armies of WordPress sites still maintained exactly this way.

Ansible

Order from Chaos

Something was still missing

  • A standard way to deploy code
  • Works for most projects out of the box
  • Documentation that actually makes sense
  • Community support — answers on StackOverflow
  • Not reinventing the wheel every single time

so we ended with yaml...

How it works


- name: Deploy PHP app
  hosts: production
  tasks:
    - name: Pull latest release
      git:
        repo: git@github.com:org/app.git
        dest: /var/www/releases/{{ release_name }}
    - name: Install dependencies
      composer:
        working_dir: /var/www/releases/{{ release_name }}
    - name: Run migrations
      command: php bin/console doctrine:migrations:migrate --no-interaction
      args:
        chdir: /var/www/releases/{{ release_name }}
    - name: Switch symlink
      file:
        src: /var/www/releases/{{ release_name }}
        dest: /var/www/current
        state: link

What got better

  • Multiple releases kept on server — rollback = flip a symlink
  • Run migrations on one node first, then roll out code
  • Rolling release — replace nodes one at a time, zero downtime
  • Native multi-node support out of the box

But...

  • Server must have PHP, nginx, php-fpm installed and configured
  • Environments drift over time — "works on staging, fails on prod"
  • Requires SSH access and Python on every target server
  • Why do I need Python on a PHP server?

The common problem

FTP, scripts, Ansible - The application and the environment were managed separately.

  • App updated regularly — environment left to age on its own
  • Dev team owned the code, ops team owned the server
  • Every upgrade became a negotiation
  • Dev environment looked nothing like prod
  • Onboarding new dev: 2–7 days of pain
  • Abandoned systems were nearly impossible to recreate

Real world: The forgotten microservice

No package mirror available for that Ubuntu version.

Found one outdated mirror – in Portugal.

Download time estimate: 7 days.

Real world: The forgotten microservice

Solution:

  • Create a LXC image from a hard drive
  • Build a local mirror of ubuntu
  • Rebuild the extension inside an LXC container
  • Ship the container
  • The whole process took a few days

Docker

The Container Revolution

The big shift

Application and environment packaged together — the image is the deployment artifact.


FROM php:7.4
COPY . /var/www/app
RUN composer install --no-dev
...
    

# docker-compose.yml
services:
  mysql:
    image: myslq:5.6.1
  php:
    build: .

Architecture

In practice: nginx + php-fpm bundled in one container, managed by supervisord


┌──────────────────────────────────┐
│             container            │
│            supervisord           │
│  ┌──────────┐   ┌─────────────┐  │
│  │  nginx   │   │   php-fpm   │  │
│  └──────────┘   └─────────────┘  │
└──────────────────────────────────┘

What got better

  • Dev = prod — same image, same behaviour*
  • Onboarding: docker compose up instead of 2–3 days
  • Rollback = pull previous image tag
  • Environment isolation per project
  • Abandoned system? Run CI every week to check if it still builds.

The pain

  • nginx + php-fpm in one container — need supervisord
  • Bundling everything together makes images large and complex
  • Heavy base images — php:8.3-fpm is ~490 MB of Debian
  • Docker alone didn't solve clustering — Docker Swarm came later
  • Databases still often run on bare metal — scaling requires planning
  • New tooling to learn: Dockerfile, networking, volumes, compose...

Why is PHP different?

PHP was designed as CGI — request → process → die

apache/nginx + php-fpm became the standard architecture for this model.

But does it have to stay that way?

php server

PHP has a built-in web server


php -S 0.0.0.0:8080 public/index.php

It works. No nginx. No php-fpm.

But...

  • Single-threaded — one request at a time
  • PHP docs: "not designed to be used on a public network"
  • Still the classic PHP model — state cleared after every request
  • Development only

Architecturally simpler — but PHP still drags along a full runtime and its dependencies.

A proof of concept. Not a solution.

ReactPHP / AmPHP

Event loop in PHP

  • Long-running PHP process — code loaded once, not per request
  • One process handles many concurrent connections
  • No nginx. No php-fpm.
  • Performance comparable to Node.js

The trade-off

  • Callback hell / promise chains — async all the way down
  • Can't use blocking PHP functions — file_get_contents, standard PDO...
  • Requires rewriting the entire application
  • Steep learning curve for PHP developers
  • CPU-intensive operations block the entire event loop

Workerman

Multi-process, synchronous PHP

  • Battle-tested in production — massively popular in China
  • Multi-process model — each worker is a separate PHP process
  • Synchronous code — write normal PHP, no async, no callbacks
  • Webman — HTTP framework built on top of Workerman

How it looks


// Normal synchronous PHP — no async required
public function index(Request $request): Response
{
    $users = User::all();
    return json($users);
}
    

php start.php start
# Workers: 4 processes
# Listening: http://0.0.0.0:8787

What you gain

  • No nginx. No php-fpm.
  • Application code loaded once per worker — not on every request
  • ~10x faster than traditional php-fpm

Limitations

  • Existing libraries work without modifications — but watch out for memory leaks
  • Long-running processes need careful state management
  • Not all frameworks work out-of-the-box — Symfony requires adapters
  • Simple apps: use Webman directly

With simplicity comes performance

No nginx. No php-fpm. Synchronous code. Fast.

Statically compiled PHP

static-php-cli

Compile PHP with all extensions baked in — no shared libraries, no OS dependencies.


bin/spc build "bcmath,curl,openssl,pdo,pdo_mysql,zip" \
    --build-cli

Result: a single php binary that runs anywhere.

FROM scratch


FROM scratch
COPY --from=builder /build/php /php
COPY --from=builder /app /app
ENTRYPOINT ["/php", "/app/start.php"]
  • Zero OS - no supply chain attacks
  • Zero shell - no shell exploits
  • Only php binary and application files

Symfony on scratch

Does it work with a full framework?

Symfony + statically compiled PHP + FROM scratch — yes, but:

  • Requires an adapter to boot Symfony inside Workerman
  • e.g. crazy-goat/workerman-bundle
  • Unusual startup model — not php bin/console server:run

What works, what doesn't

  • ✅ Routing, controllers, Twig
  • ⚠️ logs can produce OOMs (monolog, doctrine logs)
  • ⚠️ monitoring – you need write your own stuff
  • ⚠️ Users/permission, basic files that usually exist
  • ⚠️ Some things can work different - phpinfo()

Webman as a single binary

PHP + Webman + app = one file


# static-php-cli builds PHP as a self-executing stub (micro)
bin/spc build "bcmath,curl,openssl,pdo,pdo_mysql" \
    --build-micro

# Bundle app.phar into the binary
php webman build:bin
chmod +x myapp

./myapp start
# Listening: http://0.0.0.0:8787

Deploy = copy one file


FROM scratch
COPY myapp /myapp
ENTRYPOINT ["/myapp"]

The Go dream, in PHP.

Limitations

  • PHP compilation takes time — but compile once, reuse until extensions change
  • Not all extensions can be compiled statically
  • Example: New Relic — requires a dynamic .so library, won't work here
  • Still experimental territory
